# Security model

Documents, provider responses, and generated engine results are untrusted. The ingester confines files beneath the selected import root and rejects direct symlinks, unsupported formats, invalid UTF-8, malformed structures, and oversized files. The current API lets an authenticated caller select any readable server directory, so production deployments must also confine the process filesystem or add an application allowlist before accepting untrusted operators. Provider responses are validated against frozen, extra-forbidden Pydantic models before persistence. Renderers accept only typed IR; arbitrary Python, shell, engine directives, callbacks, scripting blocks, and external functions are not represented.

Requests expose time, output, and model-count limits, but local thread timeouts do not terminate native work already in progress and output is measured after worker materialization. These are caller-visible bounds, not a hard operating-system resource boundary. Native environments are recreated or reset per request. SWI-Prolog communication uses MQI-created authenticated sessions. Hosted-provider secrets are loaded from environment variables and excluded from manifests and audit details. Non-loopback API binding requires a bearer token; detailed readiness currently remains public.

Local mode isolates SWI-Prolog in its MQI subprocess but Python-native engines share the API process and environment; it is not a complete OS security boundary. The Compose profile runs the shared container as a non-root user with a read-only root filesystem, dropped capabilities, `no-new-privileges`, bounded memory/PIDs/CPU, and a persistent data-only volume. Its bridge network permits egress, including for hosted providers. True no-egress engine isolation requires separate least-privilege worker processes or containers and explicit network policy.

Report security issues privately to the repository owner. Do not include source documents, credentials, generated proprietary rules, or database contents in reports.
